# Constrained code-generation decision and usage

**Scope:** EPIC-09C only. Portable implementation and authored core checks pass;
independent final integration review passed through `8ad8421`; hosted
Windows/Linux CI passed on `7549f04`.
This decision does not complete other advanced tracks or establish AutoCAD
compatibility. Earlier independent controller reviews accepted the strict
contract, all nine renderer goldens and the independently authored validator.

## Registered output-only contract

The canonical server exposes `generate_constrained_code` alongside
`server_status`, `list_entities` and `get_entity_info`. It takes the direct,
closed recipe object, without a `recipe` wrapper:

```json
{
  "schema_version": "1",
  "template_id": "iterate_handles",
  "template_version": "1.0.0",
  "target": "python",
  "literals": {"handles": ["ABC", "000F"]}
}
```

Targets are `python`, `autolisp` and `vba`. Each supports `literal_geometry`
(bounded line/circle data), `serialize_entity_facts` (supplied facts as canonical
JSON text) and `iterate_handles` (iteration over supplied literal handles).
All template versions are `1.0.0`. Geometry creates local data only; handles
are never looked up in AutoCAD. No caller source, expression, import, template,
identifier or postprocessor is accepted. The decoder enforces the original and
normalized compact UTF-8 recipe limit of 16,384 bytes, finite number bounds,
normalized handle uniqueness and the documented scalar/text/count constraints.
Published schemas are closed and template-discriminated; schema validation
does not replace these semantic checks.

Successful JSON text has `success: true` and a sibling `artifact` field. That
artifact contains target, template ID/version, source, deterministic `sha256:`
digest, findings, `executed: false` and exactly:
`Generated text was not executed; review it outside AutoCAD MCP.`
Errors use fixed core codes/messages, including unsupported target/template/
version, payload limit and static-validation failure. Unexpected failures use
the existing redacted incident-ID path without literal/source or exception text.

## Isolation and size boundaries

Default startup and C requests import no adapter/context/capture/edit/COM module.
The existing basic service is constructed and retained after the first validated
basic invocation; invalid, unknown and C calls do not initialize it. Basic
service injection, the status resource, help prompt and all three basic tools
remain available. C routing is one stateless handler, with no service registry.

The source and actual artifact have separate 65,536-byte checks. The transport
gate independently measures the complete SDK `CallToolResult` body using
`model_dump_json(by_alias=True, exclude_none=True)` encoded as UTF-8, matching
the stdio SDK's serialization. This includes nested `response_json` escaping,
content/type fields and `isError`. The JSON-RPC request identifier is transport
metadata outside that body. Overflow returns a fixed `PAYLOAD_LIMIT` failure
without artifact/source; no truncation occurs. Existing basic-result behavior
is preserved; C failures additionally set the SDK error flag.

An actual 65,536-byte successful body passes and a 65,537-byte body rejects.
A real quote-heavy recipe produces a 53,829-byte artifact but would produce a
105,718-byte SDK body; it is refused with a 206-byte error body. Source/artifact
size alone therefore cannot establish the transport bound.

No code-generation path saves text, writes a file/clipboard, starts a process,
connects to a network, accesses credentials/environment, imports generated text,
executes it, invokes a language compiler/interpreter, calls AutoCAD or creates an
edit plan. Python parsing uses `ast.parse` with `PyCF_ONLY_AST`; it produces AST
data and does not compile generated bytecode. AutoLISP/VBA acceptance is a
conservative static subset, not a runtime execution guarantee. The catalog has
no execute/run/eval/repl/shell/apply companion.
